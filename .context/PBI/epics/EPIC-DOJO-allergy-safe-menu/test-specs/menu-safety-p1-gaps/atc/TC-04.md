## Test-level flow (not the ATC)

1. `expectNoMenusFromWeek(currentWeek)` (a profile write retires open slots of the menus of this week and later, irreversibly).
2. `withDietaryPreferencesRestored(api.profiles, ...)`: snapshot, then `setDietaryPreferences({ alergenos: row, dieta_* all false })`.
3. Positive controls: `getOwnProfile().alergenos` equals the row (sorted); `ingredientes_odiados` is empty.
4. ATC call. 5. Restore in `finally`, readback equals the snapshot.

## Fixed assertions inside the ATC

- `allergens.length > 0` (a vacuous call fails).
- For each declared allergen the catalogue holds at least one active recipe tagged with it, reported by name when not (vacuity guard).
- RPC status 200.
- Safety: the RPC result contains zero recipes tagged with any declared allergen. Mechanism: filter on the server side, `alergenos=cs.["<slug>"]` per allergen or `or=(...)`; expected `[]`. Fallback if the server-side filter is not accepted on `POST rpc`: read the result with pagination and filter in the test (R1 of the plan).
- Completeness: `count(active catalogue) - count(active catalogue tagged with any declared allergen)` equals `count(RPC result)`. Both sides come from `Content-Range` (`Prefer: count=exact`), a catalogue read against the RPC, never the RPC against itself.
- The catalogue read uses `activo=eq.true` (the RPC drops inactive recipes, line 50 of the filter migration).

Expected values: allergen sets are literals; no recipe name list is hardcoded, because the catalogue changes. Tag: none (not `@critical`: it mutates a profile).
